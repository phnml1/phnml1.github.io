## 프로젝트 한 줄 설명

창고 작업자가 주문이 배정된 셀을 선택해 QR 라벨을 발행·재출력하는 화면입니다. 키오스크는 현장 PC에 출력 요청을 보내고, 접수·실패 결과를 라벨별로 보여줍니다. 일반 택배 송장을 만드는 화면은 아닙니다.

## 해결한 업무 문제

- 라벨 데이터가 만들어져도 현장 프린터가 출력 요청을 받지 못할 수 있습니다. 작업자에게 실패한 단계를 알려줘야 합니다.
- 같은 로더의 작업도 날짜와 차수에 따라 셀·주문이 달라져, 잘못된 셀을 선택하지 않도록 범위를 좁혀야 했습니다.
- 여러 셀을 한꺼번에 처리할 때는 전체가 실패한 경우와 일부 라벨만 실패한 경우를 구분해야 했습니다.

## 나의 역할과 시스템 경계

**Frontend main:** React/TypeScript SPA, WCS·Agent API client, 셀 목록·상세, 단건 발행·재출력과 결과 기록을 직접 구현했습니다. WCS가 반환한 요청을 Agent에 전달하고, 실패가 WCS 발행·Agent 접수·결과 기록 중 어디에서 발생했는지 구분했습니다.

**Frontend 기능 브랜치:** 날짜 → 차수 → 서브차수 → 로더 → 셀 선택, 복수 셀 batch, 프린터 상태·설정·대기열 화면, 상품·수량 상세를 추가했습니다. 이 기능들의 `main` 병합과 설치본 반영은 확인되지 않았습니다.

**연계 백엔드:** 별도 WES/WCS 저장소에서 셀 주문 라벨 발행·재출력·스캔 API와 주문세트 동기화를 직접 구현했습니다. 기본 라벨 API는 해당 저장소의 `main`에 있지만 서브차수 필터는 기능 브랜치에만 있습니다. Windows Local Agent도 별도 저장소에서 직접 구성했으나, batch·대기열 제어는 그 저장소의 기능 브랜치 범위입니다. 저장소마다 반영 상태가 같다고 주장하지 않습니다.

## Technical Highlights · 대표 기술 문제

### Problem 01 - 라벨은 발행됐지만 프린터 요청은 실패할 수 있음

라벨 출력은 한 번의 요청으로 끝나지 않습니다. 서버가 라벨을 만들어도 현장 PC의 출력 프로그램이 요청을 받지 못할 수 있고, 접수 결과를 서버에 기록하는 단계가 실패할 수도 있습니다. 화면이 이를 모두 '출력 완료'로 보여주면 작업자는 무엇을 다시 해야 할지 알 수 없습니다.

### Solution 01 - 발행·출력 요청·결과 기록을 따로 표시

React 키오스크가 서버에서 받은 출력 요청을 현장 PC의 출력 프로그램(Local Agent)에 전달하고, 접수·실패 결과를 라벨별로 서버의 print-result API에 기록했습니다. 발행 실패, 출력 요청 실패, 결과 기록 실패를 구분해 안내하고 상태를 다시 조회했습니다. 출력 프로그램의 '성공'은 프린터 대기열 접수까지이며, 종이가 실제로 나왔다는 확인은 아닙니다.

### Problem 02 - 여러 라벨 중 일부만 실패하면 재출력 대상을 알기 어려움

여러 셀의 라벨을 한 번에 보낼 때 일부는 접수되고 일부는 실패할 수 있습니다. 전체를 다시 보내면 이미 접수된 라벨이 중복 출력될 수 있어, 라벨별 결과와 다시 요청할 대상을 구분해야 했습니다.

### Solution 02 - 기능 브랜치에서 셀별 출력 결과를 연결

별도 기능 브랜치에서 여러 셀을 선택해 요청하고, 현장 출력 프로그램의 응답을 라벨 ID별로 다시 연결했습니다. 프로그램이 묶음 요청을 지원하지 않을 때만 한 건씩 보내도록 했습니다. 시간 초과처럼 처리 여부를 알 수 없는 경우에는 중복 출력을 막기 위해 자동 재시도하지 않았습니다. 이 기능의 운영 설치본 반영 여부는 확인되지 않았습니다.

### Problem 03 - 잘못된 셀을 고르거나 다른 주문의 라벨을 만들 위험

같은 로더라도 작업 날짜와 차수가 다르면 라벨을 붙일 셀과 주문이 달라집니다. 키오스크가 QR 정보를 직접 조합해도 서버의 주문·상품·수량 정보와 어긋난 라벨을 만들 위험이 있었습니다.

### Solution 03 - 선택 범위를 좁히고 서버가 만든 라벨만 사용

별도 기능 브랜치에서 날짜 → 차수 → 서브차수 → 로더 순서로 선택 범위를 좁혔습니다. QR·상품·수량·출력 내용은 주문 서버(WCS)의 응답을 그대로 사용하고, 키오스크는 대상을 선택하고 확인하는 역할만 맡았습니다. 구현 당시 일부 신규 API가 응답하지 않아 전체 연동이 끝난 기능으로 소개하지는 않습니다.

## 시스템 또는 데이터 흐름

작업자가 셀을 선택하면 WCS가 주문 정보를 기준으로 라벨 ID와 출력 요청을 만듭니다. React 키오스크는 이 요청을 Windows Local Agent에 전달하고, Agent가 반환한 접수·실패 결과를 다시 WCS에 기록합니다. 마지막에는 셀 목록과 상세를 다시 조회해 화면을 WCS의 최신 상태와 맞춥니다.

## 선택한 해결 방법

- QR과 라벨 내용은 Frontend에서 조합하지 않고 WCS 응답을 그대로 사용했습니다.
- 라벨 발행, Agent 요청, 결과 기록을 서로 다른 상태로 표시해 실패 지점을 구분했습니다.
- 여러 셀을 출력할 때는 라벨별 결과를 대응시켜 실패한 항목만 확인할 수 있게 구성했습니다.

## 고려한 대안과 Trade-offs

- Frontend에서 라벨 payload를 만들면 화면 개발은 단순해지지만 WCS의 주문 원본과 어긋날 수 있어 서버 응답을 기준으로 삼았습니다.
- 실패한 batch를 무조건 다시 보내면 이미 접수된 라벨이 중복 출력될 수 있어, 처리 여부가 불명확한 timeout과 응답 유실은 자동 재시도하지 않았습니다.
- Agent 성공은 Windows spooler 접수를 뜻하며 실제 용지 배출까지 보장하지는 않습니다.

## 회고

이 화면의 핵심은 인쇄 버튼보다 책임 경계입니다. WCS가 어떤 셀의 라벨을 만들었는지, Agent가 어느 요청을 받았는지, WCS에 어떤 결과가 기록됐는지를 분리해야 현장에서 실패한 단계만 다시 판단할 수 있습니다.
