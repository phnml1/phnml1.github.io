## 대표 기술 문제

### Problem 01 - PR 화면으로 돌아올 때 변경 코드가 늦게 표시되는 문제

변경 파일이 많은 PR을 열면 화면 밖 코드까지 렌더링하느라 DOM 요소가 많아졌습니다. 특히 공동 리뷰방에서 PR 화면으로 돌아왔을 때, 처음 확인할 코드 행이 늦게 표시되는 문제가 있었습니다.

### Solution 01 - 화면에 필요한 파일의 Diff만 렌더링

파일 목록과 각 파일 제목은 유지하고, **Diff 본문은 스크롤로 가까워졌을 때 파싱하고 렌더링**하도록 바꿨습니다. `IntersectionObserver`를 사용해 화면 주변 파일을 준비하되, 선택 중인 파일이나 댓글 작성 중인 파일은 계속 렌더링합니다. 화면 밖 영역에는 높이 추정값을 남겨 스크롤 위치 변화도 줄이도록 했습니다.

PR 제목·상태는 서버에서 먼저 조회하고, 변경 파일은 별도 클라이언트 요청으로 가져오도록 분리했습니다. 이 덕분에 파일 조회가 끝나지 않아도 기본 정보를 표시할 수 있습니다.

<!-- case-result -->

**운영 PR 1건, 변경 전후 각 20회 순차 측정:** PR 복귀 후 첫 코드 행 표시 시간 중앙값 **3.259초 → 2.334초(약 28.4% 감소)**. 해당 시점의 DOM 요소 수는 **18,163개 → 1,766개**였습니다. 다른 PR이나 실제 사용자 전체의 성능을 대표하는 값은 아닙니다.

### Problem 02 - 대시보드의 느린 조회가 다른 영역까지 기다리게 함

통계 카드, 차트, 최근 PR 목록을 모두 조회한 뒤 페이지를 반환하는 구조였습니다. 최근 PR 조회가 오래 걸리면 먼저 준비된 통계와 차트도 표시되지 않았습니다.

### Solution 02 - 조회 책임을 나누고 Suspense로 점진적 표시

통계, 차트, 최근 PR을 **각각 데이터를 조회하는 Server Component**로 분리하고, 영역마다 **Suspense 경계와 스켈레톤**을 배치했습니다. 차트에 필요한 두 조회는 그 영역 안에서 병렬 실행합니다. 이렇게 하면 한 영역이 늦어지더라도 준비된 다른 영역을 먼저 전송할 수 있습니다.

<!-- case-result -->

**인위적 지연 실험:** 최근 PR 조회에 동일한 3초 지연을 넣고 로컬 프로덕션 빌드에서 전후 각 3회 측정했습니다. 이 조건에서 LCP 중앙값은 **4.194초 → 1.386초**였습니다. 적은 표본의 재현 실험이므로 실제 운영 환경에서 같은 개선 폭을 보장하지 않습니다.

**전체 변경 비교:** 인증·조회 경로 개선까지 포함한 전후 각 15회 측정에서는 대시보드 LCP p75가 **4.948초 → 4.236초(약 14.4% 감소)**였습니다. 이 수치는 Suspense만의 효과로 해석하지 않았습니다.

### Problem 03 - 원격 리뷰에서 같은 코드 위치와 의견을 맞추기 어려움

팀원이 보고 있는 파일과 줄 번호를 말로 설명해야 했고, 논의가 끝난 뒤에는 의견을 GitHub PR에 다시 등록해야 했습니다.

### Solution 03 - 위치 동기화와 음성 통화를 분리하고 GitHub 리뷰로 연결

파일·스크롤·코드 위치는 **Socket.IO**로 동기화하고, 음성 통화는 **WebRTC**로 처리했습니다. 채팅은 저장해 재접속 후에도 확인할 수 있도록 했습니다. 음성 참여는 리뷰방 참여자로 제한하고, 최대 4명까지 연결되도록 구성했습니다.

논의한 내용이 자동으로 GitHub에 게시되지는 않습니다. **사용자가 선택한 일반 리뷰 또는 코드 줄 리뷰만 게시**하며, 줄 리뷰는 최신 Diff에서 유효한 위치인지 확인합니다. 게시 실패와 오래 멈춘 요청은 다시 시도할 수 있도록 했습니다.

<!-- case-result -->

Socket·음성 훅 테스트로 참여 권한, 인원 제한, 시그널 전달, 마이크 전환과 연결 종료 시 정리를 검증했습니다. GitHub API 모의 테스트에서는 일반·줄 리뷰 게시, 오래된 코드 위치 거부, 중복 게시 복구와 권한 오류를 확인했습니다.

### Problem 04 - AI 리뷰 요청이 동시에 들어오면 중복 실행될 수 있음

버튼을 비활성화해도 다른 탭이나 여러 클라이언트에서 같은 PR의 AI 리뷰를 동시에 요청할 수 있습니다. 프론트엔드 상태만으로는 중복 작업 생성을 막기 어렵습니다.

### Solution 04 - DB 제약으로 중복 작업 생성 방지

화면에는 요청 직후 대기 상태를 표시하고, 서버에서는 진행 중인 작업을 확인합니다. **PostgreSQL 부분 고유 인덱스**로 한 PR에서 `PENDING` 또는 `IN_PROGRESS` 상태인 리뷰가 동시에 한 건만 존재하도록 제한했습니다. 동시 삽입이 충돌하면 진행 중인 작업이 있는 상황으로 처리합니다.

## 고려한 대안과 Trade-offs

- **Diff 지연 렌더링:** 모든 코드 줄을 한꺼번에 그리지 않는 대신, 특정 파일·줄로 이동하거나 작성 중인 댓글을 유지해야 합니다. 현재는 파일 단위로 렌더링 여부를 조절하고 선택 파일·댓글 작성 파일을 유지합니다. 큰 파일 내부의 행 렌더링 비용은 별도 개선 대상입니다.
- **Suspense와 Streaming:** 데이터 조회 자체가 빨라지는 기술은 아닙니다. 캐시가 유효해 모든 영역이 빠르게 준비되면 효과가 작을 수 있습니다. 병렬 조회만 했을 때와 Streaming을 적용했을 때의 차이는 독립적으로 검증할 필요가 있습니다.
- **측정 범위:** Diff 수치는 운영 PR 1건, Streaming 수치는 로컬에서 인위적 지연을 준 실험입니다. 모든 사용자 환경의 성능 개선 수치로 일반화하지 않았습니다.

## CI 검증

GitHub Actions에서 `main` 브랜치 푸시와 `main` 대상 PR에 린트·타입 검사·Jest·빌드·Playwright 검증을 실행하도록 구성했습니다.
