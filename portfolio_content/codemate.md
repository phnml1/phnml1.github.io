## 대표 기술 문제

### Problem 01 - 큰 PR에서 첫 코드가 늦게 보임

변경 파일이 많은 PR에서 보이지 않는 코드까지 한꺼번에 그리면 화면 요소가 많이 쌓입니다. PR로 돌아왔을 때 첫 코드 행이 보이기까지 오래 걸렸습니다.

### Solution 01 - 파일별 diff 본문을 가까워질 때 표시

파일 목록과 제목은 먼저 보여주고, 스크롤로 가까워진 파일의 코드 차이(diff)만 화면에 만들었습니다. 선택 중이거나 댓글을 쓰는 파일은 계속 남겨두고, 아직 표시하지 않은 영역의 높이를 유지해 스크롤 위치가 튀지 않도록 했습니다.

<!-- case-result -->

같은 운영 PR에서 변경 전후 각 20회 순차 측정한 결과, **PR로 돌아온 뒤 첫 코드 행이 보이기까지 걸린 시간** 중앙값은 3.259초에서 2.334초로, 그 시점의 DOM 요소 수는 18,163개에서 1,766개로 줄었습니다.

### Problem 02 - 함께 리뷰할 때 코드 위치가 엇갈림

원격으로 PR을 함께 검토할 때는 상대가 보고 있는 파일과 코드 위치를 말로 맞춰야 했습니다. 일반 PR 댓글만으로는 상대의 현재 위치를 알 수 없었습니다.

### Solution 02 - 공동 리뷰방에서 코드 위치와 대화를 함께 공유

공동 리뷰방에서 서로 보는 파일과 스크롤·코드 선택 위치를 Socket.IO로 실시간 공유했습니다. 코드 위치에 연결된 채팅은 DB에 저장하고, 재연결하면 API로 다시 읽습니다. 일반 PR 댓글과 알림은 공동 리뷰방과 별도 흐름으로 유지했습니다.

### Problem 03 - 같은 PR의 AI 리뷰가 중복 실행될 수 있음

사용자가 리뷰를 요청하는 순간 다른 요청도 들어오면, 두 요청이 모두 '진행 중인 리뷰가 없다'고 판단할 수 있습니다. 화면에서 버튼을 비활성화하는 것만으로는 서버의 동시 요청을 막을 수 없습니다.

### Solution 03 - 진행 중인 리뷰를 DB에서 한 건으로 제한

요청 직후 화면에 대기 상태를 표시하고, 서버에서는 진행 중인 리뷰를 먼저 조회합니다. 최종적으로 PostgreSQL의 부분 고유 인덱스가 PR마다 `PENDING` 또는 `IN_PROGRESS` 리뷰를 한 건만 허용합니다. 동시 삽입 충돌은 이미 리뷰가 진행 중인 경우로 처리합니다.

### Problem 04 - PR 기본 정보가 코드 로딩을 기다림

PR 제목과 상태는 먼저 보여줄 수 있지만, 변경 파일과 코드 차이는 별도 요청이 필요합니다. 이를 한 번에 기다리면 사용자는 기본 정보까지 늦게 보게 됩니다.

### Solution 04 - 기본 정보와 코드 영역의 로딩 분리

서버에서 접근 권한을 확인하며 PR 기본 정보를 읽어 화면에 먼저 전달합니다. 변경 파일은 클라이언트에서 별도로 불러오고, 코드 영역에 자체 로딩·오류 화면을 둡니다. diff 뷰어는 필요할 때 가져와 기본 정보 표시와 파일 표시가 서로를 기다리지 않게 했습니다.

## 채팅 저장 응답이 느린 문제

운영 협업방에서 채팅을 보내면 저장 요청의 응답까지 수초가 걸렸습니다.

<!-- case-solution -->

브라우저 요청과 Next.js `Server-Timing`을 비교해 오래 걸리는 구간을 찾고, Vercel 함수 리전을 DB가 있는 Singapore로 옮겼습니다.

<!-- case-result -->

같은 방의 **채팅 POST 응답 중앙값은 3.52초(변경 전 10회)에서 0.35초(변경 후 20회)로 줄었습니다.** 이는 화면에 메시지가 보이는 시간이 아니라 저장 요청의 응답 시간입니다.

<!-- chat-request-flow -->

#### 1단계 · 함수와 DB 사이의 리전 불일치

처음에는 Vercel 함수가 미국 `iad1`, Supabase DB 연결 지점이 Singapore에 있었습니다. 인증·방 조회·메시지 저장처럼 DB를 오가는 구간이 길어 함수 리전을 DB와 같은 `sin1`로 옮겼습니다. DB 쿼리 자체는 바꾸지 않았습니다.

| 측정 대상 · 중앙값                             | 변경 전: 함수 `iad1` · 10회 | 변경 후: 함수 `sin1` · 20회 |
| ---------------------------------------------- | --------------------------: | --------------------------: |
| 브라우저 Resource Timing의 채팅 POST 응답 시간 |                   3,522.5ms |                     351.2ms |
| Next.js `Server-Timing`의 `dbCreate` 구간      |                   1,344.3ms |                      20.1ms |

2026년 10월 13~14일, 같은 운영 PR의 기존 협업방과 같은 계정에서 순차 전송한 표본입니다. 변경 전후 날짜와 표본 수가 다릅니다. 변경 후에는 `socketEmit` 중앙값이 187.3ms(20회)로 측정된 서버 구간 중 가장 길어, 다음에는 Socket 호출 경로를 조사했습니다.

#### 2단계 · Socket 호출 경로의 지연

Next.js의 `socketEmit`은 저장한 메시지를 Socket 서버의 `/internal/emit`으로 보내고 응답을 기다립니다. Socket 서버 처리 로그와 비교하니 내부 처리 자체는 짧았습니다. Vercel 함수는 Singapore에 둔 채 Railway Socket 서버와 Redis를 US West에서 Singapore로 **함께** 옮겨 별도로 전후를 측정했습니다.

| 측정 대상 · 중앙값                          | 변경 전: Socket·Redis US West · 20회 | 변경 후: Socket·Redis Singapore · 20회 |
| ------------------------------------------- | -----------------------------------: | -------------------------------------: |
| 브라우저 CDP의 채팅 POST 시작 → 응답 헤더   |                              427.7ms |                                177.1ms |
| Next.js `Server-Timing`의 `socketEmit` 구간 |                              182.5ms |                                  9.2ms |
| Socket 구조화 로그의 `/internal/emit` 처리  |                         0.8ms (20건) |                      0.7ms (19건 대조) |

2026년 10월 14일, 같은 운영 방·계정에서 전후 각 20건을 순차 전송했고 POST 40건 모두 HTTP 201이었습니다. Socket 처리 로그는 변경 후 1건을 찾지 못해 19건만 메시지 ID로 대조했습니다. `socketEmit`에는 내부 HTTP 요청 전체가 포함되므로 Socket 처리 시간과의 차이를 순수 네트워크 왕복 시간으로 볼 수 없습니다.
