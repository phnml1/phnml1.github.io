## 프로젝트 한 줄 설명

창고 작업자가 작은 PDA와 물리 스캐너로 로케이션 → 상품 → 수량 → 분류 단계를 수행하고, 연결이 끊겨도 작업 사실과 재시도 순서를 보존하는 현장 실행 프론트엔드입니다.

## 해결한 업무 문제

- 데스크톱 전제의 화면은 640×480급 PDA에서 현재 단계와 다음 행동을 동시에 파악하기 어려웠습니다.
- Android 물리 키, 키보드 wedge, paste, 한글 IME와 Enter/Tab suffix가 섞여 스캔 값이 중복되거나 유실될 수 있었습니다.
- 네트워크 응답이 유실됐을 때 새 ID로 재전송하면 피킹 수량이 중복 반영될 수 있었습니다.
- 부분 완료분과 남은 수량을 한 task에 덮어쓰면 residual 작업과 감사 이력이 사라질 수 있었습니다.

## 대상 사용자와 사용 흐름

창고 현장 작업자는 배정된 작업을 열고 로케이션 → 상품 → 수량 → 분류 순서로 스캔합니다. 연결이 끊기면 허용된 명령을 로컬에 저장하고, 재연결 시 순차 replay합니다.

## 기여 범위와 반영 상태

### 기본 브랜치 · Frontend 직접 구현

- 작은 PDA에서 현재 단계와 다음 행동을 확인할 수 있도록 작업 화면을 구성했습니다.
- 키보드·붙여넣기·IME·WebView 이벤트를 하나의 바코드 입력 흐름으로 정규화하고, IndexedDB에 작업 명령을 보관해 재연결 시 순서대로 다시 보내도록 했습니다.
- 서버의 배정·버전·완료 응답을 PDA 작업 상태에 반영했습니다.

### 별도 기능 브랜치 · Android 및 서버 기여

- Android 물리 스캐너 입력을 WebView 이벤트로 전달하는 코드를 선행 실험에서 구현해 Picking 기능 브랜치에 이관·적응했습니다. 감사 자료 기준 기본 브랜치에도 스캐너·WebView 연결 코드는 남아 있었지만, 이관 커밋 전체가 기본 브랜치에 포함된 것은 아닙니다.
- 별도 WMS 기능 브랜치에서 작업자·장비 배정 정책과 모바일 명령의 중복 처리 방지·버전 검증을 다뤘습니다. 해당 브랜치 작업의 기본 브랜치 병합과 운영 반영은 확인되지 않았습니다.

### 로컬 Pilot · 별도 검증

- 실행 책임을 나누는 계약과 React PDA·IndexedDB, Kotlin/Spring 상태 저장을 별도 로컬 저장소에서 구현했습니다. 원격 저장소·PR·운영 배포 근거는 확인되지 않았습니다.

## 시스템 또는 데이터 흐름

1. **스캔 입력:** 물리 스캐너의 키 입력을 Android에서 완성된 바코드로 모아 WebView 이벤트로 전달합니다.
2. **작업 확인:** React 화면에서 바코드가 현재 위치·상품 단계에 맞는지 검사합니다.
3. **전송 전 보관:** 작업 명령을 IndexedDB 대기 목록에 먼저 저장하고 서버로 보냅니다. 기기에 저장된 상태는 서버 수락과 구분합니다.
4. **서버 응답 반영:** 서버의 배정·버전·완료 응답에 맞춰 다음 행동이나 충돌 상태를 보여 줍니다.

Android 입력 연결과 로컬 저장, 서버 처리의 반영 범위는 아래 ‘기여 범위와 반영 상태’에서 구분합니다.

## 핵심 상태 머신

- 화면 단계: `LOCATION → ITEM → QUANTITY → SORT → DONE`
- 오프라인 명령: `LOCAL_PENDING → REPLAYING → SERVER_ACCEPTED → LOCAL_ACKED`
- 충돌: `expectedVersion` 또는 idempotency conflict가 발생하면 자동 덮어쓰지 않고 차단 상태로 이동합니다.
- 부분 피킹: 별도 WMS 기능 브랜치에서 완료분과 residual task를 분리하고 부족 상태를 일반 완료와 다르게 처리했습니다.

## Technical Highlights · 대표 기술 문제

### Problem 01 - 바코드를 스캔했는데 값이 중복되거나 누락되는 문제

현장 PDA의 물리 스캐너는 바코드 문자와 입력 완료 키를 빠르게 보냅니다. 한글 키보드가 켜져 있거나 입력 초점이 다른 곳에 있으면 웹 입력 이벤트가 겹쳐 같은 바코드가 두 번 처리되거나 아예 누락될 수 있었습니다.

### Solution 01 - 스캐너 입력을 완성된 바코드로 전달

Android의 `dispatchKeyEvent`에서 스캐너가 보낸 문자를 모아 완성된 바코드 하나로 만든 뒤 WebView에 전달했습니다. 웹 화면에서는 키 입력·붙여넣기·한글 입력을 같은 규칙으로 처리하고, 바코드 형식 확인과 불완전 입력 경고를 넣었습니다. 장치 입력을 모으는 일은 Android가, 작업에 맞는 바코드인지 확인하는 일은 React 화면이 맡도록 나눴습니다.

### Problem 02 - 통신이 끊긴 뒤 다시 보내면 피킹 수량이 두 번 기록될 수 있음

작업자가 상품 3개를 피킹했다고 입력하면 WMS 서버가 그 수량을 저장합니다. 그런데 저장은 성공했어도 PDA로 돌아오는 응답만 끊길 수 있습니다. 이때 PDA가 새 작업으로 다시 보내면 서버에는 3개를 두 번 피킹한 것처럼 기록될 위험이 있었습니다.

### Solution 02 - 같은 작업 번호로 다시 보내고 서버 확인 후 완료 처리

PDA는 전송 전에 작업 내용과 고유 번호(`clientEventId`)를 IndexedDB의 대기 목록(outbox)에 저장합니다. 연결이 돌아오면 새 번호를 만들지 않고 같은 번호로 작업을 순서대로 다시 보냅니다. WMS가 접수했다고 확인할 때까지 대기 목록에서 지우지 않습니다. 서버에 저장된 작업 버전이 그사이 달라졌다면 자동 재전송을 멈추고 충돌 상태로 표시해, 최신 수량을 덮어쓰지 않게 했습니다.

### Problem 03 - 서버 상태만 보면 다음 작업을 알기 어려움

WMS 서버는 작업 배정, 위치 확인, 상품 확인, 수량 입력, 완료를 각각의 상태로 돌려줍니다. PDA 화면은 작업자가 지금 해야 할 행동 중심으로 구성돼 있어 서버 상태를 그대로 보여주면 다음에 무엇을 해야 하는지 알기 어려웠습니다.

### Solution 03 - 서버 응답을 작업자의 다음 행동으로 연결

WMS 응답을 PDA의 작업 단계에 맞게 연결하고, 진행 불가(`BLOCKED`), 나중에 처리(`DEFERRED`), 서버와 작업 버전이 다름(`conflict`)을 각각 다른 화면 상태로 표시했습니다. 배정·완료 여부는 WMS 응답을 기준으로 삼고, PDA에는 아직 전송하지 못한 작업만 별도로 보관했습니다.

## 연관 개발과 반영 단계

- **WMS 기능 브랜치:** React PDA·관리자 설정과 Kotlin/Spring 모바일 명령 서비스에서 작업자·장비 호환 정책, assignment version, 부분 피킹, 팔레트 복구, 출력 요청 상태를 다뤘습니다. 여러 기능 브랜치에 코드·테스트가 있지만 최신 기능의 기본 브랜치 병합과 현장 설치 버전은 확인되지 않았습니다.
- **독립 실행 로컬 Pilot:** WMS의 계획·최종 상태와 Picking 실행 책임을 분리하고 React PDA·IndexedDB와 Kotlin/Spring API를 로컬에서 검증했습니다. 별도 저장소에 원격이 없고 일부 후속 기능은 미커밋이므로 운영 시스템으로 소개하지 않습니다.
- **실기기·출력 확인:** 라벨 템플릿은 로컬 DB와 프린터로 일부 검증했지만, 같은 QR 연속 2회 출력·장시간 오프라인·전체 장비 조합은 확인되지 않았습니다.

## 선택한 해결 방법

- 한 화면에 모든 정보를 넣기보다 단계마다 목표 값과 다음 행동을 고정했습니다.
- native는 물리 입력을 안정된 event 계약으로 바꾸고, 업무 validation과 상태 전이는 React·server에 남겼습니다.
- IndexedDB transaction에 명령과 화면 projection을 함께 저장해 앱 재시작 때 torn state를 줄였습니다.
- 네트워크 전달은 at-least-once로 보고 같은 event ID를 재사용해 업무 효과를 멱등 처리하도록 설계했습니다.

## 고려한 대안과 Trade-offs

- online-only는 단순하지만 현장 네트워크 단절 동안 작업을 멈춰야 합니다. local-first outbox는 복구가 가능하지만 상태와 충돌 UX가 복잡해집니다.
- 모든 스캐너를 keyboard wedge 설정에 맞출 수 있지만 장비·IME 차이를 UI가 떠안습니다. native bridge는 안정적이지만 Android 런타임 의존성이 생깁니다.
- conflict를 항상 자동 rebase하면 작업은 빨리 이어지지만 수량과 소유권이 왜곡될 수 있어, 권위가 불명확한 경우는 차단을 선택했습니다.

## 회고

현장 프론트엔드의 성공은 버튼 클릭이 아니라 물리 입력, 로컬 영속, 서버 수락, 외부 시스템 반영이 서로 어긋나지 않는 데 있습니다. 모든 단계를 하나의 `success`로 뭉개지 않고, 사용자가 다음 행동을 판단할 수 있도록 실패 의미를 UI와 계약에 함께 담는 것이 핵심이었습니다.
