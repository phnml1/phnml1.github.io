# AI 코드 리뷰는 어디까지 진행됐을까? 알림에 진행 단계 표시하기

CodeMate에서는 GitHub Pull Request(PR)에 AI 코드 리뷰를 요청할 수 있다. 변경 파일을 가져와 AI로 분석하는 작업은 시간이 걸리기 때문에, 요청을 받으면 먼저 응답하고 분석은 서버에서 이어서 처리하도록 구성했다. 사용자는 분석이 끝날 때까지 같은 화면에 머무르지 않아도 된다.

그런데 기다리지 않아도 된다는 것과 **지금 무슨 일이 진행되고 있는지 알 수 있다는 것**은 다른 문제였다. 알림에 ‘리뷰 진행 중’이라고만 표시하면 요청이 접수된 상태인지, 변경 파일을 가져오고 있는지, AI가 실제로 분석 중인지 구분하기 어렵다. 완료 알림을 기다리는 동안에도 진행 상황을 보여줄 방법이 필요했다.

CodeMate의 AI 리뷰는 변경 파일을 조회하고, 분석하고, 결과를 마무리하는 단계를 거친다. 이 정보를 알림 목록에도 표시하기로 했다. 처음에는 알림 카드에 단계 하나를 추가하는 일처럼 보였지만, 구현을 살펴보니 **알림의 내용과 리뷰의 진행 단계가 서로 다른 데이터에서 관리된다**는 점을 먼저 이해해야 했다.

## ‘분석 중’이라는 상태만으로는 부족했다

AI 리뷰에는 크게 두 종류의 정보가 있다. 하나는 작업 전체가 어떤 상태인지, 다른 하나는 진행 중인 작업의 어느 부분을 수행하고 있는지다.

전체 상태는 `PENDING`, `IN_PROGRESS`, `COMPLETED`, `FAILED`로 구분한다. 요청이 접수됐는지, 분석이 실행 중인지, 성공적으로 끝났는지, 실패했는지를 나타낸다. 반면 세부 단계는 `FETCHING_FILES`, `ANALYZING`, `FINALIZING`처럼 분석 과정에서 현재 수행 중인 작업을 가리킨다. 화면에서 요청 직후 사용하는 임시 단계 값으로는 `QUEUED`도 있다.

예를 들어 두 리뷰가 모두 `IN_PROGRESS`여도 하나는 GitHub에서 파일을 가져오는 중이고, 다른 하나는 AI 분석 결과를 정리하는 중일 수 있다. ‘진행 중’만으로는 이 차이가 드러나지 않는다.

```text
리뷰 전체 상태                       세부 진행 단계

PENDING                              QUEUED (요청 직후 화면의 임시 값)
   ↓
IN_PROGRESS ─────────────────────── FETCHING_FILES
   │                                 ↓
   │                                ANALYZING
   │                                 ↓
   │                                FINALIZING
   ↓
COMPLETED 또는 FAILED                최종 결과 확인
```

여기서 중요한 점은 `QUEUED`가 화면에 요청 접수를 빠르게 보여주기 위해 넣는 임시 값이라는 것이다. API가 `{ status: "PENDING" }`을 응답했다고 해서 그 순간 서버의 `Review` 기록과 알림이 모두 저장됐다는 뜻은 아니다. 브라우저는 우선 캐시에 임시 상태를 반영하고, 이후 서버의 실제 리뷰 데이터를 다시 조회한다.

서버에서는 `Review`를 생성하고 작업이 진행됨에 따라 단계를 갱신한다. 따라서 **요청 직후의 화면 상태와 서버에 저장된 실제 단계 사이에는 짧은 시차가 있을 수 있다.** 알림에서 진행 상황을 보여주려면 이런 데이터의 출처까지 고려해야 했다.

## 알림의 문구와 리뷰 단계는 어디에서 가져올까?

CodeMate는 AI 리뷰 상태가 바뀔 때 알림을 생성하거나 갱신한다. 같은 사용자와 PR에 대한 AI 리뷰 알림이 이미 있으면 새로운 알림을 계속 쌓는 대신 기존 알림의 제목과 메시지를 갱신한다. 이때 읽음 여부를 다시 미읽음으로 바꾸고, 알림 생성 시각도 갱신한다. 알림이 없으면 새로 만든다.

하지만 분석 과정의 모든 세부 단계를 `Notification`에 기록하는 방식은 아니다. 알림은 **무슨 일이 발생했는지, 사용자가 읽었는지**를 관리하고, 현재 어디까지 분석했는지는 **`Review`가 관리**한다.

그래서 알림 목록 API는 목록에 포함된 알림들의 PR을 확인한 다음, 각 PR에 대한 가장 최근 리뷰의 `stage`를 조회해 알림 응답에 `reviewStage`로 덧붙인다. 알림 카드가 여러 출처의 정보를 한 번에 보여주는 셈이다.

```text
Notification
  ├─ 제목과 메시지
  ├─ 읽음 여부
  └─ 알림이 가리키는 PR
            │
            ▼
       알림 목록 API ◀──── 해당 PR의 최신 Review
            │                   └─ stage
            ▼
       알림 카드 응답
       ├─ 알림 문구 / 읽음 여부
       ├─ reviewStatus
       └─ reviewStage
```

실제 조회 로직의 의도를 단순화하면 다음과 같다. **아래 코드는 흐름을 설명하기 위한 예시이며, 원본 저장소의 코드를 그대로 옮긴 것은 아니다.**

```ts
// 알림 목록에 등장하는 PR의 식별자를 모은다.
const pullRequestIds = getPullRequestIds(notifications);

// 각 PR에서 가장 최근 AI 리뷰의 진행 단계를 조회한다.
const latestStages = await getLatestReviewStages(pullRequestIds);

// 알림 자체의 정보와 최신 리뷰 단계를 한 응답으로 조합한다.
const items = notifications.map((notification) => ({
  ...toBaseNotification(notification),
  reviewStage: latestStages.get(notification.pullRequestId) ?? null,
}));
```

이렇게 하면 `FETCHING_FILES`에서 `ANALYZING`으로 바뀔 때마다 알림 행을 새로 저장할 필요가 없다. `Review.stage`가 갱신되면 다음 알림 조회에서 최신 단계를 가져올 수 있다. 반대로 알림의 읽음 상태를 바꾸더라도 리뷰의 진행 단계와는 별개로 처리할 수 있다.

여기에는 한 가지 주의할 점이 있다. 응답의 `reviewStatus`도 현재는 `Notification` 테이블의 같은 이름의 컬럼을 직접 읽은 결과가 아니다. 알림 유형과 제목을 해석하는 호환 로직에서 값을 만든다. 따라서 현재 카드에 표시되는 값을 정리하면 다음과 같다.

| 화면에 표시하는 정보 | 현재 가져오는 곳 |
| --- | --- |
| 알림 제목·메시지·읽음 여부 | `Notification` |
| `reviewStatus` | 알림 유형과 제목을 해석한 API 응답 |
| `reviewStage` | 같은 PR의 가장 최근 `Review.stage` |

이 구분을 모르면 알림의 진행 상태도 하나의 DB 레코드에서 함께 변경된다고 생각하기 쉽다. 실제로는 **알림에 관한 정보와 분석 자체에 관한 정보를 조회 시점에 합쳐서 보여주는 방식**이다.

## 저장된 단계는 어떻게 화면에 반영할까?

서버에서 `Review.stage`를 바꿨다고 해서 열린 브라우저 화면도 자동으로 바뀌는 것은 아니다. 화면에서 새로운 값을 받으려면 다시 조회해야 한다. CodeMate는 이 부분에 TanStack Query(React Query)의 `refetchInterval`을 사용한다.

`refetchInterval`은 일정 간격으로 Query를 다시 실행하도록 설정하는 옵션이다. 이 글에서 중요한 것은 모든 화면이 하나의 주기로 갱신되는 게 아니라는 점이다. 실제 조회 주기는 화면이 보여주는 정보와 리뷰의 상태에 따라 다르다.

- **일반 PR 상세:** 리뷰가 `PENDING` 또는 `IN_PROGRESS`일 때 3초마다 조회하고, 완료·실패 후에는 주기 조회를 중단한다.
- **공동 리뷰방:** 리뷰 진행 중에는 3초, 그 외에는 15초마다 리뷰를 조회한다.
- **일반 알림 목록과 미읽음 수:** 각각 10초마다 알림 데이터를 조회한다.

상태에 따라 조회 간격을 조정하는 원리를 단순화하면 아래와 같다. 이 코드 역시 실제 훅을 복사한 것이 아니라 `refetchInterval`의 역할을 설명하는 예시다.

```ts
const reviewQuery = useQuery({
  queryKey: ["review", pullRequestId],
  queryFn: () => fetchReview(pullRequestId),
  refetchInterval: (query) => {
    const status = query.state.data?.status;

    // 분석 중일 때만 주기적으로 서버의 최신 단계를 확인한다.
    return status === "PENDING" || status === "IN_PROGRESS"
      ? 3_000
      : false; // 완료·실패 상태에서는 반복 조회를 중단한다.
  },
});
```

진행 중인 리뷰는 단계가 계속 바뀔 수 있으니 비교적 짧게 조회한다. 완료된 리뷰는 같은 빈도로 다시 요청할 필요가 적다. 반면 알림 목록은 리뷰 상세 화면과 별도의 조회 주기를 사용하기 때문에, 리뷰 상세 화면에서 먼저 보인 단계가 알림 카드에는 조금 늦게 나타날 수도 있다.

알림에서 진행 단계를 보여준다고 해서 단계가 바뀌는 즉시 사용자 화면에 도착하는 것은 아니다. 네트워크 요청 시간과 브라우저의 실행 상태도 영향을 준다. 특히 TanStack Query의 주기 조회는 기본적으로 탭이 백그라운드에 있을 때 일시 중지될 수 있다. 따라서 여기서 말하는 진행 단계는 **서버가 밀어 주는 실시간 이벤트가 아니라, 주기적으로 다시 읽은 최신 정보**에 가깝다.

또 하나 구분해야 할 것이 있다. **알림 목록이 갱신되는 것과 새로운 toast가 나타나는 것은 다르다.** CodeMate의 일반 알림 toast는 개별 알림의 문구가 바뀌었는지를 비교하지 않고, 이전 조회보다 미읽음 알림 수가 증가했는지를 기준으로 표시된다.

예를 들어 사용자가 `PENDING` 알림을 읽지 않은 채로 두었고, 서버가 같은 알림을 `COMPLETED`로 갱신했다고 생각해 보자. 알림 목록에서는 제목이 완료 상태로 바뀌지만 미읽음 알림의 *개수*는 그대로일 수 있다. 이 경우 목록에는 완료 결과가 반영되어도 새 toast가 나타난다고 보장할 수 없다.

즉, 알림 목록을 다시 조회하는 일과 사용자에게 새로운 알림이 도착했다고 알려주는 일은 현재 서로 다른 조건으로 동작한다.

## 서로 다른 시점에 갱신되는 정보의 한계

`Notification`과 `Review`를 분리하면 각 데이터가 맡은 역할은 분명해진다. 하지만 알림 목록에서 둘을 합칠 때는 다른 문제가 생길 수 있다. **합쳐진 정보가 반드시 같은 AI 리뷰 실행에서 나온 값이라는 보장이 없다는 것**이다.

한 PR에 대해 리뷰가 완료된 후 사용자가 다시 분석을 요청하는 상황을 생각해 보자. 서버에서는 기존 알림을 ‘분석 진행 중’으로 갱신할 수 있다. 그런데 새 `Review` 기록은 그보다 나중에 만들어질 수 있다. 그 사이 알림 목록을 조회하면 알림 문구는 새 분석을 가리키지만, `reviewStage`는 이전 분석에서 가장 최근에 저장된 값을 가져올 가능성이 있다.

```text
이전 리뷰: 완료됨
       │
       ├─ 재분석 요청
       │
       ├─ 알림 문구가 '진행 중'으로 갱신됨
       │       └─ 이때 알림 목록을 조회한다면?
       │          새 알림 문구 + 이전 Review의 stage가 함께 보일 수 있음
       │
       └─ 새로운 Review 생성 및 단계 기록
```

이는 실제로 이런 오류가 발생했다는 기록이 아니라, **서로 다른 쓰기 시점과 'PR의 최신 리뷰'라는 조회 기준에서 가능한 상황**이다. 현재 알림이 특정 리뷰 실행의 ID를 직접 참조하지 않기 때문에 생기는 경계이기도 하다.

이 문제를 더 엄격하게 다루려면 알림이 어느 리뷰 실행을 가리키는지 연결할 수 있어야 한다. 예를 들어 알림에 `reviewId`를 연결하면 같은 리뷰의 상태와 단계만 조합할 수 있다. 또는 알림 화면에 표시할 상태와 단계를 동일한 리뷰 레코드에서 구성하도록 응답 모델을 바꿀 수도 있다. 다만 이는 개선 방향일 뿐, 지금 적용된 구현은 아니다.

이번 작업을 하며 확인한 것은 진행 단계를 하나 추가하는 것보다 **그 단계가 무엇을 기준으로 선택되고, 언제 화면에 반영되는지**가 중요하다는 점이었다. 지금 CodeMate는 알림의 내용과 읽음 상태를 `Notification`에서, 분석의 진행 단계를 `Review`에서 가져오고, React Query로 주기적으로 다시 조회해 화면에 보여준다.

사용자는 알림 목록에서도 리뷰가 어디까지 진행됐는지 확인할 수 있다. 동시에 이 구조에서는 화면마다 조회 시점이 다르고, 알림과 리뷰가 특정 실행 단위로 묶여 있지 않다는 한계가 남는다. 앞으로 상태를 더 정확하게 보여주려면 단순히 조회 주기를 짧게 만드는 것보다, **같은 분석 작업의 정보를 일관되게 묶는 방법**부터 고민해야 할 것이다.
