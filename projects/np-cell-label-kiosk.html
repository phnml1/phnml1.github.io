Cell Label Kiosk

Case Study Summary

01 · Problem

WCS가 라벨을 발행해도 키오스크 PC의 프린터 출력은 별도 단계입니다. 셀 선택 범위, 출력 요청, 실패 결과를 한 화면에서 구분해야 했습니다.

02 · Role

React 키오스크 Frontend · WCS/Local Agent 연동 · React/TypeScript 키오스크와 WCS·Agent API client를 만들고 단건 발행·재출력·결과 기록을 연결했습니다. 배치 출력과 프린터 설정은 별도 기능 브랜치에서 구현했습니다.

03 · Verification

키오스크 초기 구조와 단건 발행·재출력은 main 커밋에 있습니다. 배치 출력·종속 필터·설정 화면은 기능 브랜치에만 있으며, 자동화된 FE 테스트와 현장 프린터 E2E 결과는 확인되지 않았습니다.

Before

발행과 인쇄 상태가 분리

라벨 생성이 성공해도 키오스크의 Agent 요청이나 결과 기록이 실패할 수 있습니다.

Decision

FE는 두 API를 연결

WCS의 agentRequest를 전달하고 단계별 오류를 나눠 표시했습니다. QR payload는 FE에서 만들지 않습니다.

After

실패 지점을 다시 확인

라벨별 출력 결과를 기록하고 셀 상태를 다시 조회합니다. 중복 출력이 안전하게 차단됐다고 주장하지 않습니다.

Verified evidence

Main branch

React SPA의 WCS·Agent client와 단건 발행·재출력·결과 기록은 FE 저장소 main 커밋에 있습니다.

Feature branch

종속 필터, 복수 셀 batch, 프린터 설정·대기열 화면은 별도 기능 브랜치의 구현입니다.

Limits & next checks

Integration status

기능 브랜치의 main 병합과 WCS 새 endpoint·Agent 설치 버전의 일치는 확인되지 않았습니다.

Print verification

FE 자동 테스트와 실제 프린터 E2E 결과는 확인되지 않았습니다. Agent 성공은 spooler 접수이며 용지 배출 보증이 아닙니다.

프로젝트 한 줄 설명

작업자가 로더 셀을 고르고 주문 라벨을 발행·재출력할 때, WCS의 라벨 상태와 키오스크 PC의 출력 요청 결과를 연결하는 React 업무 화면입니다. 이름과 달리 일반 택배 송장보다 셀-주문 QR 라벨이 중심입니다.

해결한 업무 문제

  • 라벨 발행, Local Agent 접수, WCS 결과 기록은 서로 다른 요청입니다. 한 단계의 실패를 전체 출력 성공으로 표시하면 재시도 판단이 어렵습니다.
  • 같은 로더라도 날짜·작업 차수·서브차수가 다르면 셀과 주문이 달라집니다. 수동 식별자 입력만으로는 잘못된 셀을 선택할 수 있습니다.
  • 복수 셀 출력에서 일부 WCS 발행만 실패한 경우와 프린터·Agent 전체가 준비되지 않은 경우는 다른 대응이 필요합니다.

나의 역할과 시스템 경계

Frontend main: React/TypeScript SPA, WCS·Agent API client, 셀 목록·상세, 단건 발행·재출력과 결과 기록을 직접 구현했습니다. WCS가 반환한 요청을 Agent에 전달하고, 실패가 WCS 발행·Agent 접수·결과 기록 중 어디에서 발생했는지 구분했습니다.

Frontend 기능 브랜치: 날짜 → 차수 → 서브차수 → 로더 → 셀 선택, 복수 셀 batch, 프린터 상태·설정·대기열 화면, 상품·수량 상세를 추가했습니다. 이 기능들의 main 병합과 설치본 반영은 확인되지 않았습니다.

연계 백엔드: 별도 WES/WCS 저장소에서 셀 주문 라벨 발행·재출력·스캔 API와 주문세트 동기화를 직접 구현했습니다. 기본 라벨 API는 해당 저장소의 main에 있지만 서브차수 필터는 기능 브랜치에만 있습니다. Windows Local Agent도 별도 저장소에서 직접 구성했으나, batch·대기열 제어는 그 저장소의 기능 브랜치 범위입니다. 저장소마다 반영 상태가 같다고 주장하지 않습니다.

Technical Highlights · 대표 기술 문제

Problem 01

라벨 발행과 프린터 접수를 하나의 성공으로 보기 어려움

Problem

WCS에서 라벨 ID를 받더라도 로컬 Agent나 프린터가 준비되지 않았을 수 있습니다. 반대로 출력 요청은 접수됐지만 결과 기록이 실패하면 키오스크와 WCS의 상태가 달라집니다.

Solution

FE가 WCS의 발행·재출력 응답에 담긴 agentRequest를 Local Agent에 전달하고, Agent 응답과 오류 코드를 라벨별 출력 결과 API에 기록하도록 연결했습니다. 발행 실패, Agent 요청 실패, 결과 기록 실패는 다른 안내로 표시하고 셀 목록·상세를 다시 조회합니다. Agent의 성공은 Windows spooler 접수 경계이며 물리 인쇄 완료로 단정하지 않습니다.

Problem 02

복수 셀 출력의 부분 실패와 재시도 범위

Problem

셀마다 발행·출력을 반복하면 일부 셀에서만 실패했을 때 무엇을 다시 요청해야 하는지 파악하기 어렵습니다.

Solution

현재 면·전체·실패 셀 선택을 나누고, WCS 단건 발행으로 얻은 라벨 ID와 Agent 요청을 batch로 묶었습니다. Agent의 항목별 결과를 라벨 ID 또는 순서로 대응시켜 WCS에 기록합니다. Agent가 batch route에 404/405를 반환할 때만 단건 순차 요청으로 전환합니다. timeout·5xx·응답 유실에서의 중복 출력 방지는 아직 확인되지 않았으므로 안전한 자동 재시도를 주장하지 않습니다.

Problem 03

셀 선택의 업무 문맥

Problem

로더 ID만으로 조회하면 서로 다른 차수의 셀이 섞일 수 있고, FE가 QR이나 라벨 payload를 임의로 만들면 WCS의 주문 원본과 어긋날 수 있습니다.

Solution

날짜·차수·서브차수·로더를 차례로 선택해 셀 범위를 좁혔습니다. 셀의 주문·상품·수량과 출력 payload는 WCS 응답을 사용하고 화면은 그 관계를 확인하게 했습니다. 구현 당시 일부 새 WCS endpoint는 404였다는 문서가 있어 FE 코드 존재와 실제 연동 완료는 구분합니다.

검증과 남은 경계

  • 초기 SPA와 단건 출력 연결은 해당 FE 저장소의 main 커밋에서 확인됩니다. 기능 브랜치의 batch·설정·종속 필터는 별도 범위입니다.
  • FE 저장소에는 자동화된 unit·E2E 테스트 파일이 확인되지 않았습니다. 과거 typecheck·build·로컬 브라우저 점검 기록을 운영 검증으로 바꾸어 말하지 않습니다.
  • WCS API, FE, Agent의 브랜치와 설치 버전이 일치하는지, timeout 뒤 중복 출력이 없는지, 실제 프린터가 종이를 배출했는지는 추가 확인이 필요합니다.

회고

이 화면의 핵심은 인쇄 버튼보다 책임 경계입니다. WCS가 어떤 셀의 라벨을 만들었는지, Agent가 어느 요청을 받았는지, WCS에 어떤 결과가 기록됐는지를 분리해야 현장에서 실패한 단계만 다시 판단할 수 있습니다.
