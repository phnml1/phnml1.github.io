CodeMate

GitHub PR의 변경 코드를 AI로 분석하고, 코드 위치를 공유하며 논의한 리뷰를 GitHub PR에 등록할 수 있는 공동 리뷰 서비스입니다.

서비스 열기 ↗

2026.02 - 현재 · Frontend / Full-stack

사용자
GitHub Pull Request(PR)를 검토하는 개발자와 소규모 팀
해결 과제
변경 파일이 많은 PR은 첫 코드를 보기까지 기다려야 하고, 원격 리뷰에서는 서로 보는 코드 위치와 논의 결과를 맞춰 전달하기 어렵습니다.
내 기여
PR 수집·AI 분석·diff 화면과 Socket.IO 공동 리뷰방을 구현했습니다. WebRTC 음성 대화와 GitHub PR 리뷰 등록 흐름을 추가하고, diff 표시 및 채팅 저장 요청의 지연을 측정·개선했습니다.
기술 선택 이유
큰 PR에서는 화면 밖 diff의 파싱·DOM 생성을 미루고 스크롤 높이를 보존했습니다. 공동 리뷰의 위치 공유·음성 시그널링에는 Socket.IO, 음성 전송에는 WebRTC를 사용했습니다. GitHub에 코드 줄 리뷰를 등록할 때는 최신 PR diff의 위치를 검증합니다.
결과
운영 PR 1건에서 변경 전후 각 20회 측정한 첫 코드 표시 시간 중앙값은 3.259초에서 2.334초로, 해당 시점 DOM 요소 수는 18,163개에서 1,766개로 줄었습니다.

AI 코딩 도구를 활용해 개발했고, 설계·성능 측정·검증은 직접 수행했습니다.

Case studies

문제 해결

01

큰 PR에서 첫 코드가 늦게 보임

문제

변경 파일이 많은 PR에서 보이지 않는 코드까지 한꺼번에 그리면 화면 요소가 많이 쌓입니다. PR로 돌아왔을 때 첫 코드 행이 보이기까지 오래 걸렸습니다.

구현

파일 목록과 제목은 먼저 보여주되, 첫 코드 표시를 늦추는 화면 밖 diff의 파싱·DOM 생성은 미루기로 했습니다. 스크롤로 가까워진 파일의 본문만 만들고, 선택 중이거나 댓글을 쓰는 파일은 남겨둡니다. 아직 표시하지 않은 영역은 높이를 보존해 스크롤 위치가 튀지 않게 했습니다.

확인

같은 운영 PR에서 변경 전후 각 20회 순차 측정한 결과, PR로 돌아온 뒤 첫 코드 행이 보이기까지 걸린 시간 중앙값은 3.259초에서 2.334초로, 그 시점의 DOM 요소 수는 18,163개에서 1,766개로 줄었습니다.

02

함께 본 코드와 논의 결과를 PR에 연결하기 어려움

문제

원격으로 PR을 검토할 때는 상대가 보고 있는 파일·코드 줄을 말로 맞춰야 했습니다. 대화 중 정리한 의견을 GitHub PR에도 남기려면 다시 옮겨 적어야 했습니다.

구현

선택. 공동 리뷰의 파일·스크롤·코드 선택 위치와 음성 연결에 필요한 시그널은 Socket.IO로 전달하고, 음성은 참여자 간 WebRTC 연결로 주고받습니다. 논의 내용은 먼저 CodeMate에 저장하고, 사용자가 선택한 리뷰만 GitHub PR에 등록하도록 했습니다. 실시간으로 바뀌는 참여 상태와 외부 서비스에 남는 리뷰의 경계를 구분하기 위해서입니다.

구현. 공동 리뷰방의 코드 위치에 연결된 채팅은 DB에 저장하고 재연결 시 API로 다시 읽습니다. 활성 방에 참여한 사용자만 음성에 들어갈 수 있으며, 음성 정원은 사용자 기준 4명입니다. 마이크 변경·음소거와 참여자별 재생 음량을 제공하고, 브라우저가 지원하면 출력 장치를 선택할 수 있습니다. 음성 UI와 설정 API는 기능 플래그가 켜진 경우에만 사용합니다. 일반 리뷰는 GitHub PR 리뷰 본문으로, 코드 줄 리뷰는 최신 PR diff에서 파일·줄·방향을 확인한 뒤 줄 댓글로 등록합니다. 등록 중·완료·실패 상태를 표시하고 실패하거나 오래 멈춘 전송은 다시 시도할 수 있습니다.

확인

Socket·음성 훅 테스트에서 참여 자격, 4명 제한, 시그널 전달, 마이크 전환과 연결 종료 시 정리를 확인했습니다. GitHub API를 모의한 테스트에서는 일반/코드 줄 리뷰 등록, 오래된 코드 위치 거부, 중복 등록 복구와 권한 오류를 확인했습니다.

03

채팅 저장 응답이 느린 문제

문제

운영 협업방에서 채팅을 보내면 저장 요청의 응답까지 수초가 걸렸습니다.

구현

브라우저 요청과 Next.js Server-Timing을 비교해 오래 걸리는 구간을 찾고, Vercel 함수 리전을 DB가 있는 Singapore로 옮겼습니다.

확인

같은 방의 채팅 POST 응답 중앙값은 3.52초(변경 전 10회)에서 0.35초(변경 후 20회)로 줄었습니다.

측정 조건과 상세 수치+

1단계 · 함수와 DB 사이의 리전 불일치

처음에는 Vercel 함수가 미국 iad1, Supabase DB 연결 지점이 Singapore에 있었습니다. 인증·방 조회·메시지 저장처럼 DB를 오가는 구간이 길어 함수 리전을 DB와 같은 sin1로 옮겼습니다.

측정 대상 · 중앙값변경 전: 함수 iad1 · 10회변경 후: 함수 sin1 · 20회
브라우저 Resource Timing의 채팅 POST 응답 시간3,522.5ms351.2ms
Next.js Server-Timing의 dbCreate 구간1,344.3ms20.1ms

2026년 10월 13~14일, 같은 운영 PR의 기존 협업방과 같은 계정에서 순차 전송한 표본입니다. 변경 전후 날짜와 표본 수가 다릅니다. 변경 후에는 socketEmit 중앙값이 187.3ms(20회)로 측정된 서버 구간 중 가장 길어, 다음에는 Socket 호출 경로를 조사했습니다.

2단계 · Socket 호출 경로의 지연

Next.js의 socketEmit은 저장한 메시지를 Socket 서버의 /internal/emit으로 보내고 응답을 기다립니다. Socket 서버 처리 로그와 비교하니 내부 처리 자체는 짧았습니다. Vercel 함수는 Singapore에 둔 채 Railway Socket 서버와 Redis를 US West에서 Singapore로 함께 옮겨 별도로 전후를 측정했습니다.

측정 대상 · 중앙값변경 전: Socket·Redis US West · 20회변경 후: Socket·Redis Singapore · 20회
브라우저 CDP의 채팅 POST 시작 → 응답 헤더427.7ms177.1ms
Next.js Server-Timing의 socketEmit 구간182.5ms9.2ms
Socket 구조화 로그의 /internal/emit 처리0.8ms (20건)0.7ms (19건 대조)

2026년 10월 14일, 같은 운영 방·계정에서 전후 각 20건을 순차 전송했고 POST 40건 모두 HTTP 201이었습니다.

04

같은 PR의 AI 리뷰가 중복 실행될 수 있음

문제

동시에 들어온 AI 리뷰 요청은 화면의 버튼 비활성화만으로 중복 실행을 막을 수 없습니다.

구현

화면에는 대기 상태를 바로 표시하고, 서버는 진행 중인 리뷰를 조회합니다. PostgreSQL 부분 고유 인덱스로 PR마다 PENDING 또는 IN_PROGRESS 리뷰를 한 건만 허용하고, 동시 삽입 충돌은 기존 작업이 진행 중인 경우로 처리합니다.

05

PR 기본 정보가 코드 로딩을 기다림

문제

변경 파일과 diff 요청을 함께 기다리면 이미 조회 가능한 PR 제목·상태까지 늦게 보입니다.

구현

서버에서 접근 권한을 확인하며 PR 기본 정보를 먼저 전달합니다. 변경 파일은 클라이언트에서 따로 불러오고, diff 뷰어도 필요할 때 가져와 코드 영역의 로딩·오류를 독립적으로 표시합니다.
