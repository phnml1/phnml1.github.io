Windows 키오스크 라벨 Agent

웹 화면의 라벨 요청 → ASP.NET Core localhost API → PMS 템플릿 또는 WMS ZPL 처리 → Zebra ZPL·Bixolon ESC/POS 출력 경로를 연결한 Windows Agent입니다.

  2. 02

    PMS 템플릿 조회 또는 전달된 WMS ZPL 처리

    Zebra ZPL / Bixolon 이미지·ESC/POS 경로

라벨 내용은 PMS 템플릿 또는 WMS가 전달한 ZPL에서 오고, Agent는 이를 Windows PC의 프린터에 맞는 출력 경로로 연결합니다.

01

현장 문제

PMS·WMS 웹 화면에서 라벨 출력 버튼을 눌러도 브라우저만으로는 Windows PC에 연결된 프린터와 그 명령 형식을 일관되게 다루기 어렵습니다. WinUI 3는 Windows 키오스크 앱의 틀이고, WebView2는 그 안에 웹 화면을 띄우는 구성 요소입니다. Agent는 웹 요청을 받아 PC의 프린터 출력 경로로 넘기는 로컬 프로그램입니다.

라벨 내용의 출처도 다릅니다. PMS 상품·팔레트 라벨에 필요한 템플릿은 PMS 백엔드에서 조회합니다. WMS 라벨은 WMS 백엔드가 준비해 웹 화면에서 전달한 ZPL을 우선 사용합니다. ZPL은 Zebra 계열 프린터가 이해하는 라벨 배치 명령입니다.

현장에서 다룬 프린터는 Bixolon과 Zebra입니다. Bixolon에는 40×30 mm 상품 라벨과 80×80 mm 팔레트 라벨, Zebra에는 100×100 mm WMS 출고 라벨·팔레트 라벨을 사용했습니다. 용지 규격과 라벨의 용도를 구분해 처리해야 했습니다.

02

내가 구현한 처리 흐름

  1. 요청 접수: 웹 화면이 보낸 라벨 요청을 Agent의 ASP.NET Core localhost API에서 받습니다. localhost는 키오스크가 실행 중인 같은 Windows PC를 뜻합니다.
  2. 라벨 데이터·템플릿 처리: PMS 상품·팔레트 라벨은 설정된 PMS 백엔드에서 필요한 템플릿을 조회해 라벨 데이터에 적용합니다. WMS 라벨은 웹 화면이 전달한 WMS 생성 ZPL을 우선 사용합니다. 전달된 ZPL이 없을 때만 PMS 템플릿 조회 경로를 적용합니다.
  3. 출력 경로 선택: 라벨 유형과 프린터에 맞춰 전송 형식을 정합니다. Zebra 계열에는 ZPL 경로를, Bixolon 계열에는 ZPL을 이미지로 변환한 ESC/POS 경로를 연결했습니다.

제가 맡은 범위는 로컬 API의 라벨 요청 처리, 데이터 출처에 맞는 템플릿·ZPL 적용, 프린터별 출력 경로, 그리고 프린터 설정 복원 정책입니다.

03

프린터별 분기가 필요했던 이유

같은 라벨 내용도 프린터가 해석하는 명령이 다릅니다. Zebra 계열은 라벨 배치 정보가 담긴 ZPL을 받습니다. Bixolon 계열의 해당 출력 경로는 ZPL을 그대로 보내는 대신, 라벨을 그림으로 렌더링한 뒤 ESC/POS(이미지를 전송하는 프린터 명령 형식)로 보냅니다. 상품·팔레트·WMS 출고 라벨은 용도와 용지 크기도 서로 달라, 라벨 유형과 프린터에 맞는 출력을 선택해야 했습니다.

따라서 WMS가 준비한 ZPL의 라벨 내용을 우선 보존하되, 출력 직전에 프린터 유형에 맞는 경로로 분기했습니다. Bixolon의 40×30·80×80 mm와 Zebra의 100×100 mm 용지 구분도 이 경계에 포함됩니다.
